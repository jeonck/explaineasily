# PPE·DB/데이터 세계관: 물류창고

## 무대
- 물류창고 = 데이터베이스. 재고 상자 = 데이터(레코드). 구역별 선반 = 테이블/샤딩. 출납 전표 = 트랜잭션.
- 창고 관리자(DBA)가 전체를 관리하고, 분류 담당(모델러)이 상자를 어떻게 나눌지 정하고, 포장 담당(애플리케이션)이 상자를 꺼내 쓰고, 배송 기사(요청)가 물건을 찾으러 온다.
- 배경: 낮 `sky()` = 평상시, `bad-soft` = 정합성 깨짐/장애 패널, `good-soft` = 해결·비교 패널.
- 긴장: 창고를 하나로 모아두면 관리는 편한데 너무 커지면 찾기 느리고, 여러 구역으로 나누면 빠른데 같은 재고를 복제해 둔 곳끼리 숫자가 안 맞을 위험이 생긴다 — **정규화(한곳에 정확히) vs 성능(나눠서 빠르게)**.

## 등장인물 (헬퍼는 `terms/ppedata/_world.py`)
| 인물 | 그림 | 실제 |
|---|---|---|
| 창고 관리자 | `person(..., **MANAGER)` 보라 | DBA |
| 분류 담당 | `person(..., **SORTER)` 파란 모자 | 데이터 모델러 |
| 포장 담당 | `person(..., **PACKER)` 초록 | 애플리케이션 |
| 배송 기사 | `person(..., **DRIVER)` 주황 | 클라이언트 요청 |
| 재고 감사원 | `person(..., **AUDITOR)` 노란 모자 | 정합성 점검 / 감사 |

## 소품 = 개념
| 소품 | 헬퍼 | 실제 |
|---|---|---|
| 구역별 선반 | `shelfzone()` | 샤딩 / 파티셔닝 |
| 재고 상자(twin=복제) | `box()` | 레코드 / 복제본 |
| 출납 전표 | `receipt()` | 트랜잭션 |
| 특급 출고대 | `fastdesk()` | 인메모리 DB / 캐시 |
| 다차원 색인 카드 | `indexcard()` | 다차원 색인구조 |

## 깨지는 곳
- "전부 복제해 두면 안전하다"는 반은 맞고 반은 틀리다 — 복제본끼리 숫자가 다르면(동시 수정) 더 큰 혼란이 된다. 그래서 격리 수준·병행제어 규칙이 필요하다.
- 창고를 잘게 나눌수록(샤딩) 한 번에 여러 구역을 봐야 하는 질문(조인)은 오히려 느려질 수 있다.

## 다른 세계와의 다리
- `sre`(놀이공원)의 `replication`/`consensus`/`captheorem`/`eventualconsistency` 는 분산 시스템 관점의 같은 주제를 더 깊이 다룬다 — 이 세계는 시험에 자주 나오는 데이터 모델링 기본기에 집중한다.
- `ai`(앵무새)의 `multimodal` 은 이미 다른 세계에서 다뤘다 — 여기서는 중복 설명하지 않고 링크한다.

## 이미 쓴 비유 (order 순)
| slug | 제목 |
|---|---|
| normalization | 한 칸에 한 번만 적는 규칙 |
| nosqltype | 상자 모양에 맞춰 선반을 바꾸는 창고 |
| dbsharding | 너무 커진 창고를 구역으로 쪼개기 |
| isolevel | 동시에 손댈 때 얼마나 가려 볼지 정하는 규칙 |
| lodopendata | 문을 열고 번호표를 달아 연결해두는 창고 |
| acid | 출납 전표가 지키는 네 가지 약속 |
| concurrency | 동시에 손대도 안 부딪히게 막는 규칙 |
| inmemorydb | 깊은 선반 대신 바로 꺼내는 특급 출고대 |
| scada | 창고 전체를 한눈에 보는 관제실 |
| distdb | 여러 지점으로 나뉜 창고 |
| multiindex | 여러 딱지로 한 번에 찾기 |
| dynamicsql | 그 자리에서 맞춤 주문서 쓰기 |
| raid | 선반을 쪼개고 겹쳐서 쌓기 |
| dwlake | 다듬어 둔 창고 vs 쌓아만 둔 야적장 |
| olap | 전체를 썰어보는 창고 관리자 |
| sddc | 소프트웨어로 다시 짓는 창고 |
