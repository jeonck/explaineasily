What is Per-tool Permission?

Per-tool permission, told as a story about a different badge on each drawer slot — so every tool gets only as much power as it needs.

The same key opens every single one — payment, deletion, all of it.Skip giving each tool its own scope, and everything ends up equally unlocked.

Opening everything for convenience leaves more unlocked than the job ever needed.Not knowing everything a job needs in advance makes the master key feel like the easier choice.

Each tool gets only as much power as it needs.Search can only look, payment has a limit, and deletion can't even be taken out.

Exactly as much as neededthe scope differs job by job
Read-only stays read-onlyno write power for search or lookup
Set a limitpayment gets a ceiling
Or no access at allfor risky ones like delete or refund

Each tool has its own row.Even the same apprentice gets a different scope depending on the job.

Permission is the design choice of how much to grant.A locked knife drawer isolates where a tool runs; this page is about deciding how much to grant in the first place. It's least privilege from the security world, applied one tool at a time.

In one breath

Per-tool permission = giving each drawer slot its own badge, so every tool gets only as much power as it needs. Search can only look, payment has a limit, deletion can't be taken out at all.

A design where each tool (function call) an LLM agent can use is granted its own scope — what actions it may take, over what range, up to what limit — instead of giving every tool the same blanket access: read vs. write, spending caps, which data it may reach. It's the principle of least privilege applied to the specific point of an agent's tool use, and it pairs with tool sandboxing (isolation).
