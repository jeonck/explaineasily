What is LLMOps?

LLMOps, told as a story about caring daily for a parrot that serves guests — noting note versions, logging chats, measuring beans and time, running tests, ringing the bell.

The parrot serves guests now. One day its answers went odd — and nobody knows since when, or why.It worked fine on launch day. But life after launch is the real thing — without a record you can't find when the plausible wrong answers started leaking.

The parrot, the note and the shelves keep changing with no record. And parrot answers vary anyway, so a breakdown is hard to spot.One line of the note, one shelf of the library, a new parrot version — change any one and answers shift. And with the silliness dial, the same question already varies a little each time, so eyes alone can't tell a breakdown.

LLMOps is caring for the parrot every day: note versions, chat logs, measuring beans and time, running tests, ringing the bell when something is off.Building is not the end; caring is the start. Write down every change, keep every chat, run the tests daily. That is how you can answer since when, and why.

In one breath

LLMOps = daily care for a parrot that serves guests. Version the notes, log the chats (masking secret beans), measure beans, time and refusals, test before and after changes, ring the bell when something is off. Even an unchanged bird drifts as the world changes, so keep watching.

Everything involved in operating an LLM app. Version prompts like code, trace requests, responses and tool calls into logs (with PII masking), and monitor cost, latency, refusal rate and quality scores. Catch regressions with an evaluation pipeline before deploying, and use canary releases to expose changes to a slice of traffic first. Because quality drifts as the input distribution shifts even when the model doesn't change, evaluation runs continuously.

When grown-ups say it

LLMOps
Caring for the parrot daily. The real work starts after building: write, log, measure, test, ring the bell.
Prompt versioning
Writing v3, v4 on the notes. Keep who changed what and when; roll back to the last version if things get worse. → the trainer's note
Tracing · logs
Logging the chats. Keep the question, the answer, tool notes and timings. Mask the secret beans. → secret beans
Evaluation pipeline
Automatic tests on every change. Change the note or the bird and the test runs by itself. → the examiner's scorecard
Monitoring
Watching cost, time and quality daily. Put bean cost, answer time, refusal rate and test score on the board. → the bean bill
Drift
Same bird, worse answers. Happens when the guests' questions or the world change. That is why testing is continuous, not once.
Canary release
Just one guest in ten first. Show the new note to a few guests; if the bell stays quiet, roll it out to the rest.
Guardrail
The fence. A sudden rise in answers hitting the fence means something changed. → the fence
