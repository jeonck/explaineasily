What is a Process Memory Layout?

In one breath

A process memory layout fixes zones — code, data, heap, stack — for the workspace, and dynamic memory allocation is borrowing from the heap as needed, then giving it back.

A process's virtual memory is typically laid out, from low addresses up, as the code (text) segment, the data/BSS segment for initialized and uninitialized global variables, the heap which grows via malloc/new during execution, and the stack which grows and shrinks with each function call. The heap grows from low to high addresses while the stack grows from high to low, each toward the other — colliding causes an out-of-memory error. Failing to release dynamically allocated memory with free()/delete accumulates as a memory leak.

When grown-ups say it

Code (Text) Segment
The zone holding the unchanging blueprint. Holds the program's instructions.
Data/BSS Segment
The zone for globally prepared parts. Split by whether the value is initialized.
Heap
The warehouse you draw more from as needed. Grows from low to high addresses.
Stack
The temp table that piles up and clears with each call. Grows from high to low addresses.
Dynamic Memory Allocation
Borrowing as much as needed from the heap. Borrowed with malloc/new, returned with free/delete.
Memory Leak
Space that piles up because it's never returned. Slows down long-running programs.
Stack Overflow
The temp table pushing all the way into the code zone. Common with excessively deep recursion.
Heap-Stack Collision
Heap and stack growing toward each other until they collide. A classic cause of out-of-memory errors.
